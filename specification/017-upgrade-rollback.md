# Upgrade and rollback

**Purpose.** This document defines the framework within which Heimdall versions interoperate across an upgrade or a rollback. It fixes the inter-version data-compatibility matrix on the four payload dimensions persisted across a binary swap (the Redis authoritative-zone schema, the Redis cache schema, the Redis Response Policy Zone schema, and the structured admin-RPC audit-log envelope), the deprecation windows that govern operator-facing surfaces (configuration keys, environment variables, CLI flags, and Architecture Decision Records) including the two-version compatibility commitment that this document fixes as normative, the rolling-upgrade semantics for clustered deployments (canary, bake window, automatic rollback trigger, blast-radius limits), the rollback procedure that interacts with the binary-contract drain and with the Redis schema rollback path, and the acceptance gate that prevents a release from publishing artefacts unless every UPG-* and ROLLBACK-* compatibility predicate is verifiably true on the tagged commit. It does not redefine the SemVer release process, the Tier 4 release gate, the binary boot and drain sequence, the Redis data model, the runtime-operations atomic-swap mechanism, or the operator-side procedural detail of how a rollback is executed; those questions are settled in [`010-engineering-policies.md`](010-engineering-policies.md), [`015-binary-contract.md`](015-binary-contract.md), [`013-persistence.md`](013-persistence.md), and [`012-runtime-operations.md`](012-runtime-operations.md), and the procedural detail lives in [`../docs/runbooks/rollback.md`](../docs/runbooks/rollback.md).

**Status.** Draft. The framework is fixed; concrete cadences for the deprecation windows and the bake-window default may require further calibration once production telemetry is available, and the items that remain open are listed in section 11.

**Requirement categories.** `UPG`, `ROLLBACK`.

For the project-wide principles that frame these requirements (security non-negotiable, performance as the primary guide, "Assume Nothing"), see [`../CLAUDE.md`](../CLAUDE.md). For specification-wide conventions, see [`README.md`](README.md). For the SemVer release process, the Tier 4 release gate, and the deprecation-warning obligation that precedes a `MAJOR` bump, see [`010-engineering-policies.md`](010-engineering-policies.md), in particular `ENG-167` through `ENG-185` for the release process and `ENG-072` through `ENG-075` for the Tier 4 gate. For the binary boot sequence, the drain coordinator, and the Redis pool drain, see [`015-binary-contract.md`](015-binary-contract.md), in particular `BIN-047` through `BIN-051` and `BIN-052` through `BIN-056`. For the Redis data model that the inter-version compatibility matrix governs, see [`013-persistence.md`](013-persistence.md), in particular `STORE-018` through `STORE-023` for authoritative zone data, `STORE-026` through `STORE-030` for cache entries, `STORE-031` through `STORE-036` for RPZ data, and `STORE-042` through `STORE-046` for the binary serialisation formats. For the admin-RPC surface and its audit-log envelope, see [`012-runtime-operations.md`](012-runtime-operations.md), in particular `OPS-007` through `OPS-015`, `OPS-033` through `OPS-034`, and `OPS-040`. For the structured-event taxonomy on which the audit envelope is composed, see [`007-threat-model.md`](007-threat-model.md), in particular `THREAT-080` through `THREAT-083`. For the operator-side rollback procedure that this specification anchors, see the runbook at [`../docs/runbooks/rollback.md`](../docs/runbooks/rollback.md) and the Redis recovery runbook at [`../docs/runbooks/redis-recovery.md`](../docs/runbooks/redis-recovery.md).

## 1. Scope

This document applies to every Heimdall release that produces a published artefact under the SemVer release process fixed by `ENG-167` through `ENG-185` in [`010-engineering-policies.md`](010-engineering-policies.md), and to every operator-side upgrade or rollback that traverses such a release. The framework is binding regardless of the artefact format being consumed (statically linked Linux binary, native package, OCI container, library crate publication on `crates.io`).

The scope of this document is the inter-version compatibility envelope on data and on operator-facing surfaces, the rolling-upgrade and rollback semantics expressed at the specification level, and the acceptance gate that the release process MUST satisfy. Implementation of the migration scripts, of the operator-side decision tree, and of the change-management approvals is out of scope here; the procedural detail lives in [`../docs/runbooks/rollback.md`](../docs/runbooks/rollback.md). The `MAJOR`-bump deprecation-warning obligation fixed by `ENG-169` in [`010-engineering-policies.md`](010-engineering-policies.md) is the upstream authority on when a breaking change is permissible at all; this document fixes the structural envelope within which a breaking change is admissible across an in-flight upgrade.

## 2. Definitions

For the purposes of this document, the following definitions apply.

- **Forward-compatibility.** A property of version `Vn` such that `Vn` produces persisted data (Redis payload bytes, audit-log envelope) that an earlier version `Vk` (with `k < n`) can still parse and act upon without error.
- **Backward-compatibility.** A property of version `Vn` such that `Vn` reads persisted data produced by an earlier version `Vk` (with `k < n`) without error.
- **Compatibility window.** The set of consecutive SemVer releases across which a given payload schema is forward- and backward-compatible without operator intervention.
- **Compatibility predicate.** A boolean property over a tagged commit, stating that a specific UPG-* or ROLLBACK-* requirement is verifiably satisfied on that commit. The acceptance gate fixed by section 8 is the conjunction of all such predicates.
- **Canary instance.** A single Heimdall instance in a clustered deployment that runs the new version while the remainder of the cluster continues on the previous version, used to observe the new version under live traffic before a fleet-wide rollout.
- **Bake window.** The continuous interval during which a canary instance MUST run the new version under live traffic without triggering an automatic rollback condition before the rollout is permitted to expand.
- **Blast radius.** The fraction of the cluster running a given version at any point during a rolling upgrade. A bounded blast radius is the structural mitigation against a regression that is detectable only at scale.

## 3. Inter-version data compatibility matrix

### 3.1 Normative requirements

- **UPG-001.** Every Heimdall release MUST guarantee that the four payload schemas it persists — the Redis authoritative-zone schema fixed by `STORE-018` through `STORE-023` in [`013-persistence.md`](013-persistence.md), the Redis cache schema fixed by `STORE-026` through `STORE-030` in [`013-persistence.md`](013-persistence.md), the Redis Response Policy Zone schema fixed by `STORE-031` through `STORE-036` in [`013-persistence.md`](013-persistence.md), and the structured admin-RPC audit-log envelope fixed by `OPS-040` in [`012-runtime-operations.md`](012-runtime-operations.md) and emitted under the structured-event taxonomy of `THREAT-080` through `THREAT-083` in [`007-threat-model.md`](007-threat-model.md) — are versioned by an explicit one-byte schema-version field at the head of each persisted payload, consistent with the version field already fixed by `STORE-043` in [`013-persistence.md`](013-persistence.md). A persisted payload that does not carry an explicit schema-version field MUST NOT be admitted by any release subject to this specification.

- **UPG-002.** For any two consecutive `MINOR` releases on the same `MAJOR` line, every payload schema fixed by `UPG-001` MUST be both backward-compatible and forward-compatible: a Heimdall binary at `MAJOR.MINOR.PATCH` MUST parse without error every payload produced by a binary at `MAJOR.(MINOR-1).*`, and a Heimdall binary at `MAJOR.(MINOR-1).*` MUST parse without error every payload produced by a binary at `MAJOR.MINOR.PATCH`. Forward-compatibility on optional or additive fields MUST be implemented through a structural ignore-unknown-fields rule on the parser side, not through schema-by-schema special cases.

- **UPG-003.** The compatibility window fixed by `UPG-002` applies across exactly two consecutive `MINOR` releases on the same `MAJOR` line. A release at `MAJOR.(MINOR+2).*` MAY reject a payload produced exclusively by `MAJOR.(MINOR-1).*` if and only if a deprecation event satisfying section 5 was emitted on `MAJOR.MINOR.*` and on `MAJOR.(MINOR+1).*`. On the third `MINOR` release after a deprecated payload form is introduced, write-side rejection MUST emit a clear error referencing the original deprecation event identifier and MUST cause the affected operation (zone load, cache write, RPZ write, admin-RPC envelope ingestion) to fail with a non-zero exit code on the start path or with a `FAILED_PRECONDITION` gRPC status on the runtime path, never silently.

- **UPG-004.** Across a `MAJOR` bump, the compatibility window fixed by `UPG-002` MUST NOT be assumed by default. A `MAJOR` release MAY break any payload schema fixed by `UPG-001` provided the deprecation-warning obligation fixed by `ENG-169` in [`010-engineering-policies.md`](010-engineering-policies.md) was discharged on the previous `MINOR` release on the previous `MAJOR` line and provided the release notes describe the migration path explicitly. Within a `MAJOR` bump, a one-shot operator-driven migration MAY be required; an automatic in-process migration MUST NOT be performed without explicit operator opt-in recorded in the release notes.

- **UPG-005.** The Redis authoritative-zone schema fixed by `STORE-018` through `STORE-023` MUST honour `UPG-002` on the `STORE-043` binary serialisation: the version byte already fixed at `0x01` is the schema-version field, and any additive RDATA-record extension MUST consume a higher version byte. Field-level encoding changes (the `(owner_name, qtype, qclass)` tuple encoding fixed by `STORE-042`) MUST NOT change without a `MAJOR` bump; the tuple encoding is part of the schema-stable envelope, not of the schema-versioned payload.

- **UPG-006.** The Redis cache schema fixed by `STORE-026` through `STORE-030` MUST honour `UPG-002` on the `STORE-044` binary serialisation: the 9-byte header structure (1-byte DNSSEC outcome, 4-byte insertion timestamp, 4-byte stale-until timestamp) MUST be considered part of the schema-stable envelope on the same versioning rule as `UPG-005`, and any additive cache-entry metadata MUST consume a higher schema-version byte prepended before the existing 9-byte header. Cross-version cache pollution — an older binary reading a newer cache entry it cannot understand — MUST be handled as a per-entry ignore (treat the entry as a cache miss and re-resolve), never as a cache-wide invalidation, so that a downgrade-driven cache refill does not amplify into upstream load.

- **UPG-007.** The Redis Response Policy Zone schema fixed by `STORE-031` through `STORE-036` MUST honour `UPG-002` on the action-data serialisation tracked under `STORE-034`. An additive RPZ action type MUST be carried at a higher schema-version byte; an older binary reading a newer action type it cannot interpret MUST treat the entry as `PASSTHRU` (the safe default per `RPZ-006` in [`011-rpz.md`](011-rpz.md)) and MUST emit an `upg-unknown-rpz-action` structured event under `THREAT-080` to signal the version mismatch to operators, never silently apply a partially-understood action.

- **UPG-008.** The structured admin-RPC audit-log envelope emitted by `OPS-040` in [`012-runtime-operations.md`](012-runtime-operations.md), and any extension to that envelope introduced under task #670 of the audit-fields work, MUST honour `UPG-002` through a structural rule: the JSON envelope MUST carry an explicit `"schema_version"` integer field at its top level, and consumers (log pipelines, SIEM tooling, operator dashboards) MUST be expected to ignore unknown additive fields rather than reject the envelope. Field renames or removals MUST follow the deprecation-window rule of section 5; field additions MUST NOT bump the schema-version field within the same `MAJOR` line, consistent with `UPG-002`.

## 4. Acceptance gate predicates on the data matrix

### 4.1 Normative requirements

- **UPG-009.** For every payload schema enumerated in `UPG-001`, the release process MUST execute, on the tagged commit, a predicate test that takes a sample payload produced by a build at `MAJOR.(MINOR-1).LATEST_PATCH` and verifies that the build at `MAJOR.MINOR.PATCH` parses it without error, and a second predicate test that takes a sample payload produced by the build at `MAJOR.MINOR.PATCH` and verifies that a build at `MAJOR.(MINOR-1).LATEST_PATCH` parses it without error. Both predicates MUST pass for the release to proceed past Tier 4 under section 8. The corpus from which sample payloads are drawn MUST be checked into the repository under `tests/compat/` and MUST be versioned alongside the source; ad-hoc sample generation at release time MUST NOT be permitted.

## 5. Deprecation windows

### 5.1 Normative requirements

- **UPG-010.** Every operator-facing surface — TOML configuration keys exposed under [`001-server-roles.md`](001-server-roles.md), [`002-transports.md`](002-transports.md), [`014-forward-zones.md`](014-forward-zones.md), and any other configuration-file entry; environment variables exposed under `BIN-009` through `BIN-014` in [`015-binary-contract.md`](015-binary-contract.md); command-line flags exposed under `BIN-001` through `BIN-005` in [`015-binary-contract.md`](015-binary-contract.md); and Architecture Decision Records governing operator-visible behaviour under `ENG-112` through `ENG-127` in [`010-engineering-policies.md`](010-engineering-policies.md) — MUST follow the same two-version compatibility commitment fixed by `UPG-002`. A surface introduced at `MAJOR.MINOR.PATCH` MUST remain accepted (read-side) for at least the next two `MINOR` releases on the same `MAJOR` line; write-side rejection on the third `MINOR` release MUST emit a clear error referencing the original deprecation event identifier, consistent with `UPG-003`.

- **UPG-011.** A deprecation event MUST be recorded as a structured `upg-deprecation-announced` event under `THREAT-080` at the moment the surface enters its deprecation window, and as a structured `upg-deprecation-removed` event at the moment the surface is removed. The deprecation event MUST carry, at minimum, a stable identifier (a UUIDv7 generated at deprecation time and persisted in the repository under `docs/process/deprecations.md`), the surface kind (`config-key`, `env-var`, `cli-flag`, `adr`), the surface name, the version in which deprecation was announced, the version in which removal is scheduled, and the migration path (the replacement surface, or the documented operator action). The same identifier MUST be referenced in the release notes of every subsequent release until removal, and in the rejection error emitted under `UPG-003`.

- **UPG-012.** The deprecation window for an Architecture Decision Record under `ENG-120` in [`010-engineering-policies.md`](010-engineering-policies.md) is structurally distinct from a payload-schema deprecation: the ADR `status` field already encodes `deprecated` and `superseded-by ADR-NNNN`, and `ENG-122` mandates retention of deprecated and superseded ADRs as historical record. This document does not override that mechanism; it adds the obligation that, when a deprecated or superseded ADR governs operator-visible behaviour (configuration shape, runtime contract, on-disk artefact format), the deprecation window of `UPG-010` applies to that operator-visible behaviour even if the underlying ADR has already transitioned to `deprecated` or `superseded-by`. The two mechanisms (ADR status lifecycle, operator-surface deprecation window) MUST be reconcilable on every release; a release that retires operator-visible behaviour without satisfying both mechanisms MUST be rejected by the Tier 4 gate under section 8.

## 6. Rolling-upgrade semantics for clustered deployments

### 6.1 Normative requirements

- **ROLLBACK-001.** A clustered Heimdall deployment — two or more Heimdall instances serving the same logical service behind a load-balancer, an anycast prefix, or an equivalent traffic distribution mechanism — MUST be upgradeable through a rolling-upgrade procedure that bounds the blast radius and admits an automatic rollback trigger before any operator approval. The procedure MUST be expressible as a sequence of three structurally distinct phases: a canary phase (a single instance on the new version, the rest on the previous version), a bake window during which the canary serves live traffic and is observed against the SLO commitments fixed by [`016-slo-sli.md`](016-slo-sli.md), and an expansion phase that increases the new-version fraction in bounded steps until the cluster has converged.

- **ROLLBACK-002.** The canary phase MUST be limited to exactly one instance regardless of cluster size. A multi-instance canary MUST NOT be admitted by this specification; the structural reason is that an automatic rollback trigger fired during the canary phase MUST be able to revert exactly one instance, and the per-cell SLO error-budget computation under `SLO-011` and `SLO-012` in [`016-slo-sli.md`](016-slo-sli.md) MUST attribute the budget consumption unambiguously to the new-version subset.

- **ROLLBACK-003.** The bake window MUST be a continuous interval of at least 30 minutes during which the canary instance has not triggered any of the automatic rollback conditions fixed by `ROLLBACK-005`. The 30-minute floor is calibrated against the 5-minute SLI window fixed by `SLI-001` through `SLI-005` in [`016-slo-sli.md`](016-slo-sli.md), giving the multi-window multi-burn-rate alerting under `SLO-013` of that file at least six independent SLI samples to settle into the post-upgrade distribution. Operators MAY configure a longer bake window for changes that touch the cryptographic policy or the DNSSEC validator; operators MUST NOT configure a shorter bake window.

- **ROLLBACK-004.** The expansion phase MUST NOT exceed a 25% blast-radius increment per step on a cluster of 8 or more instances, and MUST NOT exceed a 50% blast-radius increment per step on smaller clusters. Each step MUST observe a per-step bake window of at least the 5-minute SLI window fixed by [`016-slo-sli.md`](016-slo-sli.md) before the next step is admitted; an automatic rollback trigger fired during any step MUST revert the entire fleet to the previous version, not merely the most recent step.

- **ROLLBACK-005.** The automatic rollback triggers during the canary phase, the per-step bake window, and the post-upgrade observation window MUST include at minimum: a `slo-burn-fast` event under `SLO-013` in [`016-slo-sli.md`](016-slo-sli.md) attributable to the new-version subset; a `/readyz` predicate failure under `OPS-024` and `OPS-042` in [`012-runtime-operations.md`](012-runtime-operations.md) on the new-version instance for more than 60 seconds; a panic-abort exit (exit code 70 under `BIN-046` in [`015-binary-contract.md`](015-binary-contract.md)) on the new-version instance; and a `bogus` DNSSEC validation rate exceeding the `SLO-007` ceiling on the new-version instance over a 5-minute window. The trigger set MUST be evaluated automatically by the deployment-side orchestration; a human-driven decision MUST NOT be on the critical path for the canary-phase trigger.

## 7. Rollback procedure

### 7.1 Normative requirements

- **ROLLBACK-006.** The rollback procedure MUST sequence the binary swap behind the controlled drain fixed by `BIN-047` through `BIN-049` in [`015-binary-contract.md`](015-binary-contract.md) and the Redis pool drain fixed by `BIN-051` in the same file. New connections MUST stop being accepted before the in-flight queries on the outgoing version are allowed to complete, and the Redis connection pool MUST be drained without torn writes on the outgoing version before the new (rolled-back) version is started. This sequencing MUST be honoured regardless of the artefact format being swapped (container image, native package, raw binary). The operator-side procedural detail of how to invoke this sequence per artefact format lives in [`../docs/runbooks/rollback.md`](../docs/runbooks/rollback.md) and MUST NOT be duplicated in this specification.

- **ROLLBACK-007.** The Redis schema rollback path MUST honour the structural invariant that the rolled-back (older) binary parses Redis payloads produced by the rolled-forward (newer) binary under the compatibility window fixed by `UPG-002`. When a payload was produced by a binary outside that window — specifically, by a binary at `MAJOR.(MINOR+2).*` whose payloads exercise an additive schema-version byte that the rolled-back binary at `MAJOR.MINOR.*` cannot parse — the rolled-back binary MUST treat the affected entry as a per-entry parse failure under `UPG-006` (cache) or as a per-zone load failure causing the role-assembly fail-closed path under `BIN-021` in [`015-binary-contract.md`](015-binary-contract.md) (zone data). The operator-side recovery from that condition is documented in [`../docs/runbooks/rollback.md`](../docs/runbooks/rollback.md) section 4 and in [`../docs/runbooks/redis-recovery.md`](../docs/runbooks/redis-recovery.md); the spec-level invariant is that no silent data-loss path exists, and that the failure mode is observable through structured events under `THREAT-080`.

- **ROLLBACK-008.** Operator pre-flight checks MUST be enumerated as a checklist that the rollback procedure MUST satisfy before the binary swap is initiated. The checklist MUST include, at minimum: confirmation that the previous version's artefact (container image, package, or tarball) is present in the artefact store; confirmation that Redis is reachable and healthy from the host on which the swap will occur; confirmation that the previous version's `/version` and `/readyz` outputs are known and recorded; and confirmation that a change-management approver has been notified consistent with the audit-log obligation under `OPS-040` in [`012-runtime-operations.md`](012-runtime-operations.md). The checklist content lives in the operator runbook at [`../docs/runbooks/rollback.md`](../docs/runbooks/rollback.md); the spec-level obligation is that the checklist exists and is honoured before the binary swap starts.

## 8. Acceptance gate

### 8.1 Normative requirements

- **UPG-013.** A Heimdall release MUST NOT publish artefacts under the SemVer release process fixed by `ENG-167` through `ENG-185` in [`010-engineering-policies.md`](010-engineering-policies.md) unless every UPG-* and ROLLBACK-* compatibility predicate enumerated by this document is verifiably true on the tagged commit. The acceptance gate MUST be evaluated as part of the Tier 4 release gate fixed by `ENG-072` through `ENG-075` in [`010-engineering-policies.md`](010-engineering-policies.md) and as the Tier 4 gate framework as extended under Sprint 64 task #666; a release that fails any UPG-* or ROLLBACK-* predicate MUST be blocked at the artefact-publication step, in the same manner that a missing signed artefact under `THREAT-013` or a missing Software Bill of Materials under `THREAT-014` blocks publication today.

- **UPG-014.** The compatibility predicates required by `UPG-009` MUST be encoded as automated tests under the integration-harness work fixed by `ENG-203` in [`010-engineering-policies.md`](010-engineering-policies.md), so that the acceptance gate is mechanical rather than procedural. A failure of any compatibility predicate MUST emit an `upg-acceptance-gate-failed` structured event under `THREAT-080` and MUST surface in the release-cut workflow as a blocking status check.

## 10. Rationale

The upgrade-and-rollback framework is the deployment-side counterpart of the source-tree-side release framework already fixed by [`010-engineering-policies.md`](010-engineering-policies.md). The release framework guarantees that a tagged commit passes the Tier 4 gate before artefacts are produced; this framework guarantees that an artefact moving forward through an upgrade or backward through a rollback does not silently corrupt persistent state, does not leave operator-facing surfaces in a partially-migrated condition, and does not permit an automatic rollout to amplify a regression beyond a bounded fraction of the cluster. Without the framework, the SemVer commitments of `ENG-167` through `ENG-185` are upstream of artefact production but silent on what the deployed service does at the moment of the swap, which is exactly the surface where most regressions are observable and where most data-loss incidents originate.

The two-version compatibility commitment fixed by `UPG-002` and `UPG-010` is calibrated against operator practice rather than against a pure-engineering optimum. A one-version window would make every `MINOR` release a forced upgrade for operators who skip releases (a common reality on cautious operations teams), and would put the project's release cadence directly at odds with the operations cadence. A three-version window would push the deprecation-removal point past the structural memory of most release teams (the third release after deprecation announcement is, at the project's three-to-six-month `MINOR` cadence under `ENG-174`, between nine and eighteen months out), at which point the original deprecation event is forgotten and the removal lands as a surprise. Two versions match the practical pattern: an operator who skips one release is still safe; an operator who skips two is on notice from the release notes of the intervening release; an operator who skips three has been signalled twice and has had between six and twelve months to act.

The structural ignore-unknown-fields rule on parsers (`UPG-002`) is the canonical mechanism that decouples additive schema evolution from the version-bump cadence. The alternative — schema-by-schema special cases on the parser side, with explicit if-version-then-parse-this-field branches — produces parser code that grows linearly with the number of past versions and that is structurally indistinguishable from a re-introduction of the parser-vulnerability classes that the threat model under `THREAT-080` and `THREAT-082` exists to mitigate. The ignore-unknown-fields rule is also the mechanism on which the JSON audit-log envelope evolves under `UPG-008`, so that log pipelines, SIEM tooling, and operator dashboards do not break when Heimdall adds a new field to the envelope.

The cross-version cache-pollution policy under `UPG-006` (treat the entry as a cache miss and re-resolve, never invalidate the whole cache) is the safe-by-construction choice. A whole-cache invalidation on a downgrade would amplify into upstream load at exactly the moment when the deployment is least stable, potentially driving upstream authoritative servers into rate-limiting territory and producing a secondary outage on top of the downgrade incident. A per-entry ignore is bounded by the queries the deployment naturally serves and degrades gracefully into the same warm-up shape that any cold cache exhibits.

The single-instance canary under `ROLLBACK-002` is calibrated against the per-cell SLO accounting fixed by [`016-slo-sli.md`](016-slo-sli.md). A multi-instance canary would muddy the burn-rate attribution: the new-version subset's burn would be averaged across instances, potentially masking an instance-level regression behind cluster-level smoothing. A single canary keeps the attribution clean and makes the automatic rollback trigger under `ROLLBACK-005` operate on a signal that is not statistically diluted. The 30-minute bake window under `ROLLBACK-003` is a structural floor (six SLI samples at the 5-minute window fixed by [`016-slo-sli.md`](016-slo-sli.md)), not a one-size-fits-all default; operators MAY extend it for sensitive changes (cryptographic policy, DNSSEC validator) but MUST NOT shorten it, because shortening below six SLI samples would drive false-positive rollbacks on transient noise as readily as it would catch genuine regressions.

The blast-radius limits under `ROLLBACK-004` (25% per step on clusters of 8+, 50% per step on smaller clusters) reflect the same calibration. On large clusters, 25% is the smallest practical step size that still expands within a reasonable rollout window; smaller steps would produce a rollout horizon long enough that operator attention drifts and the procedure becomes prone to skipped checks. On small clusters, 50% is necessary because 25% rounds down to zero new-version instances on a 4-instance cluster, which is a structural impossibility; the 50% step size on small clusters keeps the rollout finite while still bounding the blast radius below the cluster majority.

The drain sequencing under `ROLLBACK-006` extends the binary-contract drain mechanism rather than redefining it. The drain coordinator under `BIN-047` is already the structural answer to "how does Heimdall stop accepting new traffic without dropping in-flight work"; the rollback procedure simply applies that mechanism in the order required for a binary swap to be loss-free. The Redis pool drain under `BIN-051` is the structural answer to "how does Heimdall ensure no torn writes leak across the swap"; the rollback procedure honours that obligation explicitly. Neither mechanism is novel to the rollback path; the spec-level decision in `ROLLBACK-006` is that the existing mechanisms are the canonical mechanism here too, and that the rollback procedure does not introduce a separate, parallel drain.

The acceptance gate under `UPG-013` and `UPG-014` is the structural enforcement that this framework is not aspirational. A release that fails a compatibility predicate but ships anyway would invalidate the framework on every subsequent release, because operators would correctly conclude that the predicates are advisory rather than blocking. Coupling the predicates to the Tier 4 gate fixed by `ENG-072` through `ENG-075` makes them mechanical: a CI failure on `UPG-009` blocks the same way a CI failure on `cargo deny check` blocks today, and the same release-cut workflow that today blocks on a missing signed artefact also blocks on a missing compatibility predicate. The Sprint 64 task #666 work that extended the Tier 4 gate framework is the implementation surface on which `UPG-013` and `UPG-014` land; no new release-process construct is introduced.

## 11. Open questions

The framework fixed by sections 3 through 8 is complete given the decisions already settled in [`010-engineering-policies.md`](010-engineering-policies.md), [`013-persistence.md`](013-persistence.md), [`015-binary-contract.md`](015-binary-contract.md), [`012-runtime-operations.md`](012-runtime-operations.md), and [`016-slo-sli.md`](016-slo-sli.md). The items below remain open and MUST NOT be assumed before they are decided.

- **Cluster-deployment topology specification.** This document refers to "a clustered Heimdall deployment" without fixing the topology vocabulary (anycast, DNS-load-balancer pool, Kubernetes Deployment with replica count, generic load-balancer pool). Whether a separate specification file is required to fix the cluster-deployment vocabulary, or whether [`009-target-environment.md`](009-target-environment.md) is the right home for that vocabulary, is open.
- **Bake-window default beyond the 30-minute floor.** `ROLLBACK-003` fixes a 30-minute structural floor and admits operator extension upward. Whether a higher project-wide default (60 minutes, 120 minutes) should be preferred, and what telemetry should drive a future revision of the default, is open and depends on production observability that is not yet available.
- **Blast-radius increment for cluster sizes between 4 and 8.** `ROLLBACK-004` fixes a 25%-or-50% bimodal rule keyed on the 8-instance threshold. Whether intermediate cluster sizes (4, 5, 6, 7 instances) should follow a more granular rule is open.
- **Persistence of deprecation-event identifiers.** `UPG-011` mandates that every deprecation event carry a UUIDv7 identifier persisted under `docs/process/deprecations.md`. The exact format of that file (CSV, TOML, structured Markdown, automated index), the cross-link between the file and the structured event, and the responsibility for its maintenance are open and depend on whether the deprecation register is hand-authored or generated from CI.
- **Compatibility predicate corpus location and lifecycle.** `UPG-009` mandates a sample-payload corpus under `tests/compat/`. The exact corpus structure, the rule for refreshing samples on each `MINOR` release, and the policy on retiring samples for versions outside the two-version compatibility window are open.
- **Audit-log envelope schema-version evolution.** `UPG-008` mandates an explicit `"schema_version"` integer field on the audit-log envelope but does not fix the initial value or the rule for incrementing it across `MAJOR` lines. Whether the field is a single integer or a pair `(major, minor)` mirroring the SemVer line is open.
- **Canary trigger sensitivity tuning.** `ROLLBACK-005` enumerates a structurally minimal set of automatic rollback triggers. Whether additional triggers should be included by default (e.g. cache hit-rate drop below `SLO-005` and `SLO-006` floors during canary, panic count above a threshold short of full panic-abort, an upstream-reachability drop on the forwarder role) is open and depends on operational experience.
- **Forward-compatibility test responsibility.** `UPG-009` requires both a backward and a forward-compatibility predicate. The forward-compatibility predicate requires a `MAJOR.(MINOR-1).LATEST_PATCH` build to be available at release time for `MAJOR.MINOR.PATCH`; the mechanism for keeping such a build available (cached binary in the artefact store, on-demand checkout-and-build in the release pipeline, dedicated reference image) is open.
